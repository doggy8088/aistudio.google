    Live API 功能指南¶

    Live API 目前為預覽版。

    本指南完整說明 Live API 提供的各項功能與設定。 如需總覽與常見使用情境的範例程式碼，請參閱開始使用 Live API 頁面。

    開始之前¶

    • 先熟悉核心概念： 如果尚未讀過，請先閱讀開始使用 Live API 頁面。 該頁面會介紹 Live API 的基本原理、運作方式，以及不同的實作方式。
    • 在 AI Studio 中試用 Live API： 在開始開發之前，先在 Google AI Studio 試用 Multimodal Live API 會很有幫助。如要在 Google AI Studio 中使用 Live API，請選取 Stream。

    模型比較¶

    下表彙整了 Gemini 3.8 Live、 Gemini 3.8 Live Extended Thinking、 Gemini 3.1 Flash Live Preview 與 Gemini 2.5 Flash Live Preview 之間的主要差異：

    功能 Gemini 3.8 Live Gemini 3.8 Live Extended Thinking Gemini 3.1 Flash Live Preview Gemini 2.5 Flash Live Preview

    傳送音訊¶

    音訊必須以原始 PCM 資料傳送（原始 16 位元 PCM 音訊、16kHz、小端序）。

    # Assuming 'chunk' is your raw PCM audio bytes

    audio=types.Blob(
        data=chunk,
        mime_type="audio/pcm;rate=16000"
    )
)

    // Assuming 'chunk' is a Buffer of raw PCM audio
session.sendRealtimeInput({
  audio: {
    data: chunk.toString('base64'),
    mimeType: 'audio/pcm;rate=16000'
  }
});

    音訊格式¶

    Multimodal Live API 中的音訊資料一律為原始、小端序的 16 位元 PCM。音訊輸出的取樣率一律為 24kHz。輸入音訊 原生為 16kHz，但 Multimodal Live API 會在需要時重新取樣， 因此可以傳送任何取樣率。如要表明輸入音訊的取樣率，請將每個包含音訊的 Blob 的 MIME 類型設為 audio/pcm;rate=16000 之類的值。

  async function waitMessage() {
    let done = false;
    let message = undefined;

      if (message) {
        done = true;

        done = true;
      }

  }

    model: model,
    callbacks: {
      onopen: function () {
        console.debug('Opened');
      },
      onmessage: function (message) {
        responseQueue.push(message);
      },
      onerror: function (e) {
        console.debug('Error:', e.message);

    語音活動偵測（VAD）¶

    語音活動偵測（VAD）讓模型能辨識使用者何時在說話。這對於打造自然的對話至關重要，因為它讓 使用者可以隨時打斷模型。

    當 VAD 偵測到打斷時，正在進行的生成會被取消並 捨棄。只有已經傳送至用戶端的資訊會保留在 工作階段記錄中。伺服器接著會傳送一則 BidiGenerateContentServerContent 訊息來回報這次打斷。

    Gemini 伺服器接著會捨棄所有待處理的函式呼叫，並傳送一則 帶有已取消呼叫 ID 的 BidiGenerateContentServerContent 訊息。

    async for response in session.receive():
    if response.server_content.interrupted is True:
        # The generation was interrupted

        # If realtime playback is implemented in your application,
        # you should stop playing audio and clear queued playback here.

    const turns = await handleTurn();

for (const turn of turns) {
  if (turn.serverContent && turn.serverContent.interrupted) {
    // The generation was interrupted

    // If realtime playback is implemented in your application,
    // you should stop playing audio and clear queued playback here.
  }
}

    自動 VAD¶

    依預設，模型會對連續的音訊輸入串流自動執行 VAD。VAD 可以透過 設定組態 的 realtimeInputConfig.automaticActivityDetection 欄位來設定。

    當音訊串流暫停超過一秒時（例如 因為使用者關閉了麥克風），應傳送 audioStreamEnd 事件來清除所有快取的音訊。用戶端可以隨時恢復傳送 音訊資料。

import { GoogleGenAI, Modality } from '@google/genai';

async function live() {
  const responseQueue = [];

  async function waitMessage() {
    let done = false;
    let message = undefined;
    while (!done) {
      message = responseQueue.shift();
      if (message) {
        done = true;
      } else {
        await new Promise((resolve) => setTimeout(resolve, 100));
      }
    }
    return message;
  }

  async function handleTurn() {
    const turns = [];
    let done = false;
    while (!done) {
      const message = await waitMessage();
      turns.push(message);
      if (message.serverContent && message.serverContent.turnComplete) {
        done = true;
      }
    }
    return turns;
  }

  const session = await ai.live.connect({
    model: model,
    callbacks: {
      onopen: function () {
        console.debug('Opened');
      },
      onmessage: function (message) {
        responseQueue.push(message);
      },
      onerror: function (e) {
        console.debug('Error:', e.message);
      },
      onclose: function (e) {
        console.debug('Close:', e.reason);
      },
    },
    config: config,
  });

  // Send Audio Chunk
  const fileBuffer = fs.readFileSync("sample.pcm");
  const base64Audio = Buffer.from(fileBuffer).toString('base64');

  session.sendRealtimeInput(
    {
      audio: {
        data: base64Audio,
        mimeType: "audio/pcm;rate=16000"
      }
    }

  );

  // if stream gets paused, send:
  // session.sendRealtimeInput({ audioStreamEnd: true })

  const turns = await handleTurn();
  for (const turn of turns) {
    if (turn.text) {
      console.debug('Received text: %s\n', turn.text);
    }
    else if (turn.data) {
      console.debug('Received inline data: %s\n', turn.data);
    }
  }

  session.close();
}

async function main() {
  await live().catch((e) => console.error('got error', e));
}

    混合式 VAD¶

    混合式 VAD 結合了自動 VAD（穩健的語音開始偵測）與手動 VAD（低延遲的回應定稿）的優點。

    在此設定下：

    1. 伺服器上的自動 VAD 保持啟用。伺服器會自動 偵測使用者語音的開始，並使用前置填充來避免截斷 話語的開頭。
    2. 用戶端使用用戶端 VAD 來偵測使用者何時 停止說話。
    3. 當用戶端 VAD 偵測到語音結束時，會向伺服器傳送 audio_stream_end 訊號。
    4. 伺服器將 audio_stream_end 訊號視為立即 定稿的提示，繞過預設的伺服器端靜音偵測 延遲，並以最低延遲傳回轉錄文字與模型回應。
    5. 如果用戶端 VAD 未能觸發，伺服器端 VAD 會作為 備援，偵測語音結束。

    請注意，如果用戶端 VAD 閾值設定得太積極，可能會導致 語音被截斷。不過，這種方式能避免手動 VAD 可能發生的 開頭截斷問題。

    # Set up with automatic VAD enabled (default)
config = {
    "response_modalities": ["AUDIO"],
}

async with client.aio.live.connect(model=model, config=config) as session:
    # Send audio data normally
    await session.send_realtime_input(
        audio=types.Blob(data=audio_bytes, mime_type="audio/pcm;rate=16000")
    )

    # When client-side VAD detects the end of speech, send:
    await session.send_realtime_input(audio_stream_end=True)

    // Set up with automatic VAD enabled (default)
const config = {
  responseModalities: [Modality.AUDIO],
};

// Send audio data normally
session.sendRealtimeInput({
  audio: {
    data: base64Audio,
    mimeType: "audio/pcm;rate=16000"
  }
});

// When client-side VAD detects the end of speech, send:
session.sendRealtimeInput({ audioStreamEnd: true });

    停用自動 VAD¶

    或者，你也可以在設定訊息中將 realtimeInputConfig.automaticActivityDetection.disabled 設為 true 來停用自動 VAD。在此設定下，用戶端負責偵測使用者 語音，並在適當時機傳送 activityStart 與 activityEnd 訊息。在此設定下不會傳送 audioStreamEnd。串流的任何中斷 都會以 activityEnd 訊息標示。

    config = {
    "response_modalities": ["AUDIO"],
    "realtime_input_config": {"automatic_activity_detection": {"disabled": True}},
}

async with client.aio.live.connect(model=model, config=config) as session:
    # ...
    await session.send_realtime_input(activity_start=types.ActivityStart())
    await session.send_realtime_input(
        audio=types.Blob(data=audio_bytes, mime_type="audio/pcm;rate=16000")
    )
    await session.send_realtime_input(activity_end=types.ActivityEnd())
    # ...

    const config = {
  responseModalities: [Modality.AUDIO],
  realtimeInputConfig: {
    automaticActivityDetection: {
      disabled: true,
    }
  }
};

session.sendRealtimeInput({ activityStart: {} })

session.sendRealtimeInput(
  {
    audio: {
      data: base64Audio,
      mimeType: "audio/pcm;rate=16000"
    }
  }

);

session.sendRealtimeInput({ activityEnd: {} })

    了解 VAD 參數及其對品質的影響¶

    使用自動 VAD 時，有兩個關鍵參數控制音訊在傳送至模型之前 如何被切分為語音輪次：

    • prefixPaddingMs：在偵測到語音之前要納入的音訊量。 這段「回溯」能確保模型擷取到語音完整的 起始部分，包括可能在 VAD 觸發前就開始的第一個音節。值為 0 可能會導致 字詞的開頭被截斷。
    • silenceDurationMs：伺服器在結束語音輪次之前，等待靜音持續的 時間。這決定了系統對句中自然停頓（例如思考、呼吸或 子句邊界）的容忍程度。

    silenceDurationMs 對音訊品質的影響¶

    silenceDurationMs 的值會直接影響模型接收處理的音訊區塊大小與完整性：

    • 建議值（500ms–800ms）： 兼顧良好的平衡——模型 接收到完整、上下文豐富的音訊區塊，同時延遲保持在 合理範圍。伺服器的內部預設值約為 800ms。
    • 太低（例如 100ms–200ms）： 系統會在自然停頓時結束語音輪次， 將單一話語切成多個小型音訊 片段。模型會逐一接收這些片段，因而失去 跨片段的上下文，導致轉錄與回應 品質降低。
    • 太高（例如 2000ms 以上）： 系統會在使用者停止說話後等待很長 時間，增加模型回應前使用者感受到的延遲。

    手動（用戶端）VAD 的最佳做法¶

    當你停用自動 VAD，並透過自己的用戶端語音偵測管理 activityStart/activityEnd 訊號時，請注意伺服器內建的音訊緩衝機制會被繞過。這表示：

    1. 沒有語音前緩衝： 伺服器不再於偵測到的語音開始之前 前置音訊。你的用戶端應在傳送 activityStart 之前納入足夠的音訊 上下文。
    2. 沒有靜音容忍： 伺服器會立即依你的 activityEnd 訊號行動，不再額外等待。如果你的用戶端 VAD 使用積極的語音結束閾值（例如 200ms 的靜音）， 語音可能會在自然停頓時於句中被截斷。

    如要以手動 VAD 維持音訊品質，請在用戶端的語音活動偵測器中使用至少 500ms 的語音結束靜音 閾值。低於此值的閾值常會導致音訊片段化，進而降低 轉錄與模型回應品質。

    token 數量¶

    你可以在傳回的伺服器訊息的 usageMetadata 欄位中找到已消耗的 token 總數。

    async for message in session.receive():
    # The server will periodically send messages that include UsageMetadata.
    if message.usage_metadata:
        usage = message.usage_metadata
        print(
            f"Used {usage.total_token_count} tokens in total. Response token breakdown:"
        )
        for detail in usage.response_tokens_details:
            match detail:
                case types.ModalityTokenCount(modality=modality, token_count=count):
                    print(f"{modality}: {count}")

    const turns = await handleTurn();

for (const turn of turns) {
  if (turn.usageMetadata) {
    console.debug('Used %s tokens in total. Response token breakdown:\n', turn.usageMetadata.totalTokenCount);

    for (const detail of turn.usageMetadata.responseTokensDetails) {
      console.debug('%s\n', detail);
    }
  }
}

    媒體解析度¶

    from google.genai import types

config = {

const config = {
    responseModalities: [Modality.AUDIO],
    mediaResolution: MediaResolution.MEDIA_RESOLUTION_LOW,

    你可以為包含音訊、影片或圖片輸入的多模態工作階段設定 mediaResolution。mediaResolution 會調整視覺輸入每一影格的 token 配置，而音訊串流在所有解析度設定下都以每秒固定速率進行 Tokenizer。詳情請參閱 媒體解析度 指南。

    限制¶

    在規劃專案時，請留意 Multimodal Live API 的以下限制。

    回應模態¶

    原生音訊模型僅支援 `AUDIO 回應模態。如果你需要 以文字形式取得模型回應，請使用輸出音訊轉錄 功能。

    用戶端驗證¶

    Multimodal Live API 依預設僅提供伺服器對伺服器驗證。如果你採用 用戶端對伺服器方式 實作 Multimodal Live API 應用程式，你需要 使用臨時 token 來降低安全性 風險。

    工作階段時長¶

    僅音訊的工作階段上限為 15 分鐘，音訊加影片的工作階段 上限為 2 分鐘。不過，你可以設定不同的 工作階段管理技術，讓工作階段時長不受限制地延長。

    上下文視窗¶

    每個工作階段的上下文視窗上限為：

    • 原生音訊輸出 模型為 128k token
    • 其他 Multimodal Live API 模型為 32k token
